app/order · api/order/v1 · HTTP 8003 / gRPC 9003

购物车与订单

order 服务同时管购物车和订单：购物车只存「谁、哪个 SKU、几件」，价格每次现取；下单按请求号幂等、以商品服务价格为准、先占库存再写单，失败就脱离请求上下文把预占放回去；订单的每一步状态变化都是带「当前状态」的条件更新，并在同一事务里写发件箱事件。
15个 RPC对外契约CartService 4 个，OrderService 11 个
5种状态订单状态机待支付 1 · 已支付 2 · 已发货 3 · 已完成 4 · 已取消 5
30分钟支付截止预占过期再多 5 分钟；发货满 7 天自动收货
5个主题发件箱事件order.created / paid / cancelled / shipped / completed

01这个模块负责什么#

order 是交易链路的中枢：上游是 gateway、payment、product，下游是 product、inventory、user 三个服务。

调用方gateway：买家与后台路由payment：MarkOrderPaid / ListPaidOrdersproduct：GetOrderItem / MarkOrderItemReviewed
→
order 服务CartService · OrderServiceSweeper 每分钟扫描Streams 每秒投递发件箱
→
下游（gRPC）product 9001：CheckSellable / BatchGetSkus / IncreaseSalesinventory 9002：GetStocks / ReserveStock / ConfirmReservation / ReleaseReservationuser 9000：GetAddress

购物车 新增

本库 cart_items，下单时直接读本库，不跨服务。

下单与订单 新增

八步下单、取消、确认收货、后台列表与发货。

对内接口 仅 gRPC

支付通知、对账取数、评价核对与回写，没有 HTTP 路由。

订单状态机

每分钟扫描做四件事

NewSweeper 启动即跑一次，之后每分钟一次，每轮 30 秒超时，每类每批 200 张。

  1. 关超时单ListExpiredPending：待支付且 expires_at <= now，按截止时间升序 → CancelIfPending(timeout) → 释放
  2. 补释放ListUnreleased：已取消且 stock_released = false → 再调一次释放
  3. 补确认ListUnconfirmed：已支付 / 已发货 / 已完成，且未确认、未标终态失败 → confirmStock
  4. 自动收货ListShippedBefore(now - 7d) → 与买家确认收货走同一个 finish

05关键规则与失败处理#

MarkOrderPaid 判定表

订单当前状态支付单时间结果
已支付相同—成功，顺带补 confirmStock
已发货 / 已完成相同—成功，什么都不改
待支付—≤ 截止 + 5 分钟条件更新为已支付 → confirmStock
待支付—> 截止 + 5 分钟按 timeout 关单并释放 → 409
已取消任意—409 ORDER_STATUS_CONFLICT
已支付及之后不同—409
条件更新没抢到——重读：同一支付单算成功，否则 409

确认库存的三种结果

ConfirmReservation 返回订单侧处理扫描还会捞吗
成功stock_confirmed = true不会
RESERVATION_NOT_FOUND / RESERVATION_STATUS_CONFLICT打 ALERT 日志，stock_confirm_failed = true不会，需人工处理
超时、连不上等其它错误只记日志，订单仍是已支付会，下一分钟重试
!
终态失败意味着钱收了、库存没扣预占已被释放或找不到，重试也扣不到库存，所以落标记后不再重试，靠告警日志人工介入。

下游错误怎么翻译

下游返回order 返回
ReserveStock · STOCK_INSUFFICIENT409 ORDER_STOCK_INSUFFICIENT
ReserveStock · 其它任何错误503 ORDER_UPSTREAM
BatchGetSkus · PRODUCT_NOT_SELLABLE400 ORDER_ITEM_NOT_SELLABLE，否则 503
GetAddress · NotFound / BadRequest400 ORDER_ADDRESS_NOT_FOUND，否则 503
ReleaseReservation · RESERVATION_NOT_FOUND当作释放成功
购物车 CheckSellable · 不可卖400 PRODUCT_NOT_SELLABLE，否则 503

07已知遗留#

正确性

库存业务错误被当成 503 错误码

现象
orderStock.Reserve 与 mapReservation 的默认分支把 STOCK_NOT_FOUND、STOCK_INVALID_ARGUMENT 也映射成 ORDER_UPSTREAM
影响
前端和调用方会把确定性失败当成可重试的下游不可用

购物车行数并发可超 100 并发

现象
Count 与 Create 不在同一事务，也没有行级锁
影响
同一用户并发加不同 SKU 时可以突破上限

体验与冗余

立即购买会删掉车里同 SKU 整行 体验

现象
下单成功后无条件 RemoveSKUs(本次 SKU)，不区分来源
影响
车里原有 5 件、立即购买 1 件，整行都没了

完成订单时销量走了两条路 冗余

现象
finish 仍同步调 IncreaseSales，同时 MarkCompleted 写 order.completed 给 product 消费
影响
product 用 sales_applies 按订单 + 商品去重，不会重复加；但同步调用没必要，仍耦合 product 可用性
