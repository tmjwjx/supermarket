app/notification · pkg/kafkaout · HTTP 8005 / gRPC 9005

通知与事件

业务改动和写发件箱在同一个事务里，改了就一定有事件；每个服务每秒把没投递的事件推到 Kafka，消费方靠 consumed_events 去重、原地退避重试、按分区只提交连续处理完的一段；notification 把订单和支付事件写成站内信。
7个主题事件清单order 5 个，payment 1 个，product 1 个
3个消费组消费方notification · product-sales · inventory-sku
1秒投递间隔每批最多 100 条，按创建时间
5次连续失败才跳过等待从 200ms 起翻倍，函数封顶 3 秒

01这个模块负责什么#

事件只用在「做完了告诉对方一声、对方失败也不影响我」的地方；预占、确认、释放和支付通知仍是同步调用。

pkg/kafkaout 新增

  • Insert：事务内写发件箱
  • StartPublisher：每秒投递
  • StartConsumer：拉取、重试、提交
  • Brokers：读各服务 yaml 的 kafka.brokers

各服务的发件箱 新增

product、order、payment 各有一张 outbox_events，由各自的 Streams 拉起投递循环。

notification 服务 新增

消费订单和支付事件，写站内信；给买家列表、未读数和标记已读。

02变更点#

能力规则落点
同事务写事件状态变更抢到才写，和业务一起提交kafkaout.Insert(tx, …)
投递每秒取 100 条未投递的，全部发成功再标记publishLoop
Kafka 地址逗号分隔；为空时 127.0.0.1:9092Brokers()
连不上只记日志，进程照常服务kafka client / kafka produce 日志
消费去重事件 id 写进 consumed_events，和业务同事务SaveOnce
原地重试200ms 起翻倍，封顶 3 秒；连续 5 次失败跳过retryDelay · maxAttempts
提交偏移关自动提交，按分区只交连续处理完的一段consumeBatch
缺事件头用「主题/分区/偏移」当 ideventFrom

03实现逻辑#

从业务事务到站内信

③投递循环 publishLoop
客户端
franz-go；拨号 2 秒、单次生产 3 秒、记录不重试、投递 4 秒超时，允许自动建主题
一批
ProduceSync 5 秒超时，取 FirstErr()，有一条失败就整批不标记
停机
各服务的 NewStreams 返回取消函数，由 Wire 的清理链调用
⑤消费循环 consumeLoop
拉取
每次最多等 2 秒；除超时和取消之外的拉取错误，关客户端 1 秒后重连
分组
按「主题 + 分区」分组，组内按偏移升序逐条处理
提交
每个分区处理完就提交一次；提交用 WithoutCancel 加 3 秒，停机时也能交掉已处理的
中途返回
只有在重试等待时停机才会停下，失败那条和它后面的都不提交

原地退避的等待时间

按分区只提交连续处理完的一段

05关键规则与失败处理#

notification 收到一条事件

情况Accept 返回结果
主题不在文案表里成功忽略
payload 不是 JSON错误原地重试，5 次后跳过
user_id 解析失败成功丢弃，不写站内信
事件 id 已在 consumed_events成功不重复写
写库失败错误原地重试
没有 order_id—用 payment_id 填关联 id

投递和拉取出错

出错位置处理
建生产客户端记 kafka client，下一秒再建
读发件箱记 outbox pending，下一秒再读
发送（任一条）记 kafka produce，关客户端，整批下一秒重发
标记已投递记 outbox mark delivered，下次重复发送
拉取记 kafka fetch，关客户端 1 秒后重连
提交偏移记 kafka commit，下次拉取可能重复收到
i
Kafka 挂了不影响下单和支付业务事务照常提交，事件在发件箱里排队；Kafka 恢复后按创建时间补发。

07已知遗留#

投递与存储

发件箱整批 FirstErr 可能卡住 投递

现象
一批 100 条里只要有一条始终发不出去（比如超大消息），整批都不标记，下一秒又是同一批
影响
这个服务后面所有事件都停在发件箱里

outbox_events 不清理 容量

现象
投递后只把 delivered 改成 true，没有删除或归档
影响
表只增不减，delivered 索引的选择性越来越差

接口与分层

站内信列表不分页 接口

现象
ListNotificationsRequest 没有分页字段，ListByUser 一次取全部
影响
老用户的消息越多，接口越慢、响应越大

biz 直接依赖 pkg/kafkaout 分层

现象
各服务 biz/*/stream.go 拉起投递和消费，Accept 的入参是 kafkaout.Event
影响
biz 认识了存储与消息驱动，和仓库规范里「biz 只认 DO」不符

notification 自带一张没人写的发件箱 冗余

现象
datanote.OutboxEvent 和 kafkaout.Row 映射到同一张 outbox_events，投递循环每秒空跑
影响
多一次每秒查询，OutboxEvent 上「本轮不连接 Kafka」的注释也已过时
