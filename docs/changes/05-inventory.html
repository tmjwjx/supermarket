01这个模块负责什么#

库存服务只回答两件事：每个 SKU 还能卖几件，以及某个订单占住的货最后是扣掉还是还回去。它不认识商品和价格，只认 SKU id 和订单 id。

调用方调用时机
productCreateStock保存商品后、上架校验时补建
product（Kafka）product.sku.created新 SKU 落库后经发件箱投递
order 购物车GetStocks展示每个 SKU 的可卖数量
order 下单ReserveStock过期 = 下单 + 30 分钟 + 5 分钟余量
order 支付ConfirmReservation支付成功后；订单扫描兜底重试
order 关单ReleaseReservation用户取消或支付超时
gatewayGetStocks 等 3 个买家公开查；后台查与调整

02变更点#

库存服务这次从空壳变成完整实现。先看一个 SKU 的三个数字怎么算，再看每种操作改哪个数。

操作on_handreserved可卖成立条件
入库 AdjustStock +n+n0+n行存在
出库 AdjustStock −n−n0−n调整后可卖 ≥ 0
预占 Reserve q0+q−q可卖 ≥ q
确认 Confirm q−q−q0on_hand ≥ q 且 reserved ≥ q
释放 Release q0−q+qreserved ≥ q

建档幂等 CreateStock

给 SKU 建一条 0 库存的行；主键冲突（MySQL 1062）就返回已有行，重复调用、重复消费都安全。

后台调整 AdjustStock

delta 不能为 0；reason 留空时按正负填 inbound / outbound；只认 product / super 角色。

两个查询 Get

GetStocks 公开，AdminGetStocks 需后台身份；同一套逻辑，去空去重，查不到的 SKU 不返回。

按订单预占

同订单同 SKU 数量先合并；SKU 排序后逐个条件更新，任一不够整单回滚；同订单重复预占直接成功。

确认 · 释放

先锁住该订单的预占行再动库存；重复确认、重复释放都成功且不重复扣减；已释放再确认返回冲突。

过期与建档

后台协程每分钟释放已过期的占住预占；消费 product.sku.created 自动建库存行。

库存流水
每次数量变化在同一事务写一条 stock_logs：前后 on_hand、前后 reserved、order_id、reason。
reason 取值
inbound · outbound · reserve · confirm · release；后台调整可自填，种子脚本填 seed。

03实现逻辑#

预占的生命周期

一张订单在 stock_reservations 里每个 SKU 一行，状态 1 占住、2 已确认、3 已释放。确认和释放只能从「占住」出发，终态之间互不可转。

环节 1预占 ReserveStock一个事务
入参
order_id 非空、expire_unix > 0；同 SKU 数量合并，数量必须 > 0，否则 400。
幂等检查
先数该订单在 stock_reservations 里的行，有就直接返回成功。
逐个占库存
按 SKU id 排序后执行 UPDATE stocks SET reserved = reserved + q WHERE sku_id = ? AND on_hand - reserved >= q，影响 0 行就记进「不够」名单（没有库存行也算不够）。
整单回滚
名单非空就回滚整笔事务，返回 409 STOCK_INSUFFICIENT，消息带上所有不够的 SKU。回滚前再数一次，若并发请求已为同订单写好预占，则当作成功。
写预占行
每个 SKU 一行，状态占住，带过期时间；撞 uk_order_sku 唯一索引也当作成功。
环节 2确认 / 释放一个事务
锁预占行
SELECT … FOR UPDATE WHERE order_id = ? ORDER BY sku_id，并发的同订单请求在这里排队，后到的能看到先到者已提交的状态。
没有行
返回 404 RESERVATION_NOT_FOUND。
状态分拣
挑出占住的行；遇到对立终态（确认遇已释放、释放遇已确认）直接 409；一个占住都没有就返回成功。
动库存
确认：on_hand −q, reserved −q，条件两者都 ≥ q。释放：reserved −q，条件 reserved ≥ q。条件不成立返回 409。
改状态
UPDATE … WHERE id = ? AND status = 1，影响 0 行同样 409，整笔回滚。
环节 3过期扫描 Sweeper后台协程
节奏
进程启动立刻跑一次，之后每分钟一次，每轮限时 30 秒。
取数
status = 1 AND expires_at <= now，按订单分组、最早过期优先，最多 200 单；走索引 idx_status_expires。
执行
逐单调用和 ReleaseReservation 相同的释放逻辑；一单失败不影响后面，只记第一条错误日志。

同一订单再次调用时的判定

当前预占状态ConfirmReservationReleaseReservationReserveStock
无预占404 NOT_FOUND404 NOT_FOUND正常预占
占住扣实物，改已确认还回，改已释放直接成功

场景返回数据变化
sku_id 为空或 delta 为 0400 STOCK_INVALID_ARGUMENT无
调整的 SKU 没有库存行404 STOCK_NOT_FOUND无

订单侧怎么接这些错误
订单确认库存时，冲突或预占不存在视为终态：打 ALERT 日志并标记 StockConfirmFailed，不再重试；其它错误（超时、不可用）留给订单扫描重试。

07已知遗留#

预占与确认 / 释放的加锁顺序相反

重复预占不看已有状态 幂等缺口

幂等分支只数「该订单有没有行」。预占已被释放（例如过期）后再调 ReserveStock 会直接返回成功，但并没有重新占库存，后续确认会得到 409。

公开查询过于透明 暴露面

GetStocks 不需登录，返回精确的 on_hand、reserved、available；sku_ids 个数不设上限，一次可拼很大的 IN 查询。
