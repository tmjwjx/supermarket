01这个模块负责什么#

两个前端只和 gateway 说话。gateway 自己不存数据，只负责验签、按路径查角色、把身份转给上游。

只开 HTTP

kratos.Server(hs) 只挂一个 HTTP 服务器，不暴露 gRPC 端口，也不连数据库。

先验签再转发

登录与后台模式验签失败就返回，不会打到上游。

按路径查角色

后台路由用 httpauth.AllowAdmin，和各服务 HTTP 端口是同一套规则。

身份随调用走

验签得到的 id 与角色写进 x-md-global-*，上游 service 层从元数据读。

02变更点#

上一版 gateway 只转 user 的三条路由；这次扩到全部服务，并把鉴权拆成四种模式、两把密钥。

能力之前现在
路由3 条，只转 user86 条，覆盖七个服务
上游一条 user 连接七条连接，16 个客户端
鉴权模式只有 requireToken公开、可选、登录、后台
身份转发只验签，不转身份写 x-md-global-* 元数据
密钥auth.jwt_secret 一把再加 auth.admin_jwt_secret，必须不同
后台令牌无HS256 + aud=admin + role
超时自身与上游都是 1000 毫秒自身 7000，order 6000，其余 1000
中间件recoveryrecovery + tracing.Server
配置读取env.NewSource("KRATOS")只读 yaml 文件

03实现逻辑#

四种模式

模式由路由注册时套的包装函数决定，每条路由上方都有一行注释写明模式。公开路由不套任何包装，直接进入 call。

gate三个包装函数
requireLogin
tokens.Verify 失败直接返回错误；成功把 sub 写成 x-md-global-user-id
optionalLogin
验签成功且 sub 非空才写身份，否则什么都不写，照样往下走
requireAdmin
admins.Verify 取 id 与 role，allowAdmin(URL.Path, role) 不过返回 GATEWAY_FORBIDDEN
验签器
auth.Verifier / auth.AdminVerifier，分别包 httpauth.VerifyUser / VerifyAdmin
stamp · call身份怎样到达上游
写入
stamp 用 metadata.AppendToClientContext 把键值挂到请求 context 上
转发
call 设 operation 后走中间件链，forwardIdentity 把这些键复制进 gRPC 调用的 context
发送
拨号时挂的 metadata.Client() 把元数据带到上游，tracing.Client() 传 trace
不转的
gateway 没挂 metadata.Server()，客户端自带的 x-md-* 头进不了转发元数据

超时嵌套

下单时 order 还要再调 user 取地址、product 取商品、inventory 预占库存，耗时明显长于其他调用。三层超时必须由外到内递减，外层才能拿到内层的明确错误，而不是自己先超时。

gateway 自身7000ms
gateway 调 order6000ms
order 服务端5000ms
调其余上游1000ms

来源：app/gateway/configs/config.yaml 的 server.http.timeout_ms 与 client.*.timeout_ms；order 服务端取自 app/order/configs/config.yaml。

05关键规则与失败处理#

场景结果错误
公开路由，带不带令牌直接转发，不写身份—
可选路由，令牌无效照样转发，不写身份—
登录路由，无令牌 / 签名错 / 过期不转发401 UNAUTHORIZED
登录路由，令牌无 sub 或非 HS256不转发401 UNAUTHORIZED
后台路由，拿买家令牌后台密钥验签失败401 UNAUTHORIZED
后台令牌 aud 不是 admin不转发401 UNAUTHORIZED
后台令牌有效，角色不符不转发403 GATEWAY_FORBIDDEN
启动时密钥为空或两把相同记日志后退出exit 1
客户端自带 x-md-global-* 头不进入转发元数据—
✓gateway 放行不等于最终放行

各服务 HTTP 端口有 httpauth.Server 再验一次，service 层还会按自己的规则读元数据，例如 /v1/users/{id} 是否本人由 user 服务核对。

06验证与测试#

进程内下单链路

TestCheckoutFlowOrder 在本机随机端口起一个 gRPC 假服务，把 gateway 的 HTTP handler 直接接上去。每个假实现被调到时往 seq 里追加一个词，最后比对顺序。

真实环境端到端

make e2e 跑 TestCheckoutThroughGateway，要求所有服务已启动并跑过 make seed。地址写死为 http://127.0.0.1:8080。

  1. 注册 + 登录拿买家令牌
  2. 列表 + 详情挑一个启用且有价的 SKU
  3. 加购 + 地址cart/items、addresses
  4. 下单带 request_id
  5. 建支付 + 模拟成功payments、:simulate
  6. 30 秒内已支付轮询订单 status=2
  7. 60 秒内有通知轮询 notifications

07已知遗留#

!各服务 gRPC 端口对外监听，且信任元数据

七个服务的 gRPC 都监听 0.0.0.0:9000–9006，中间件只有 recovery、tracing.Server、metadata.Server，不验签。能连上端口的人自带 x-md-global-admin-role: super 就拿到超级权限，app/product/cmd/seed 正是这样直接调 gRPC 的。

!角色判断找不到路径时默认放行给商品运营

AllowAdmin 的 default 分支允许 product 与 super。以后新增的后台路径只要没在 switch 里登记，就会自动对商品运营开放，而不是默认拒绝。
